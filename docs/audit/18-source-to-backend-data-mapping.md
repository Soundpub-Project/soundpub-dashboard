# 18 — Source-to-Backend Data Mapping

Date: 2026-11-25
Status: **SCHEMA-BASED MAPPING DRAFT — NOT ROW-VALIDATED; DO NOT USE FOR CUTOVER**

## Purpose and evidence boundary

This is a concrete source-to-target mapping based on the 33 tables in `docs/migration/CANONICAL_SCHEMA.sql` and the target schema created by `backend/migrations/0001`–`0082`. It includes related Supabase Auth and Storage objects, which are outside those 33 `soundpub` tables.

No source rows, Auth users, sessions, refresh tokens, financial history, or Storage objects were read for this mapping. The backup verification opened only its schema artifact. The backup and canonical definitions already have documented differences; therefore every mapping must first be checked against the exact approved source snapshot. This is a mapping specification, not an ETL program or proof that source data satisfies target constraints.

## Global conversion rules

1. **User identity is a crosswalk, never a name/email match.** Use source `auth.users.id` as the legacy key. Provision one target `backend_users.id` per resolved source identity and persist the exact relation in a controlled staging crosswalk; the current dry-run derives namespace-scoped deterministic UUIDv8 candidates. Create `external_identities.source_system/source_auth_user_id` bindings only when the provider issuer and subject are independently verified. Resolve all legacy user foreign keys through the crosswalk. A missing or ambiguous identity is an orphan: record it in `identity_references` where appropriate and block dependent writes. Never guess based on email, name, phone, or row order.
2. **Do not import credentials or sessions.** Do not copy password hashes, access/refresh tokens, verification/reset tokens, or active sessions. Require reauthentication/password setup. Create provider identities only when their issuer and subject are independently verified; profile SSO labels alone are insufficient.
3. **Imported roles remain unverified.** Source `user_roles.created_at` is not proof of backend authorization approval. Do not populate target `verified_at` from it. Backend authorization requires verified roles; role activation requires a separate reviewed approval. The source has no `tenant_id`, so the current converter emits review candidates only and does not create target role rows or assign a tenant.
4. **Preserve domain IDs only after target-emptiness and collision checks.** Keep source UUIDs for domain records where the target key is the same business record and all references can be reconciled. Record every changed ID in a durable crosswalk. Replays must be idempotent and must stop on a conflicting pre-existing target row; never truncate or overwrite target data to make a run pass.
5. **Money uses exact decimal arithmetic.** Convert IDR amounts to minor units as exact decimal-string `amount * 100`; reject values with unsupported precision, overflow, inconsistent currency, or unexplained disagreement among legacy amount columns. Do not use JavaScript floating point. Never seed the backend balance from cached profile balances or revenue totals.
6. **Storage metadata does not move bytes.** For each retained file, inventory the source bucket/key, copy bytes to the private target provider, verify size/MIME/SHA-256, then create `storage_assets`/`media_objects` and bind the domain row. A URL or path alone is not proof that the object exists or is private.
7. **Unknown or unsupported data is quarantined, not dropped silently.** Every source row must have exactly one disposition: converted, rejected with a reason, or preserved in an approved restricted archive. Conversion totals and rejected/orphan counts must reconcile to source counts.

### Royalty, payout, and payment amounts

- Parse source `numeric(18,2)` as decimal text; require exact cent precision and IDR unless a source row proves another currency. Compute minor units without floating point.
- `royalties` contains `pendapatan_kotor_dsp`, `pendapatan_label_artis`, `pendapatan_bersih_soundpub`, `artist_revenue`, `soundpub_revenue`, `label_revenue`, and `net_revenue`. These are not assumed additive or interchangeable. A signed finance owner must select the authoritative columns and demonstrate per-upload, per-beneficiary, and total reconciliation before mapping to `gross_amount`, `deduction_amount`, `net_amount`, allocations, and ledger events.
- For payout history, source request amount, `payout_balance_reservations`, profile balances, processed statuses, and proof objects must reconcile together. Every imported target payout requires allocations plus the matching reservation and terminal ledger event, audit row, and outbox evidence. Do not create approval/reviewer facts absent from the source.
- For `balance_adjustments`, the target's approved manual adjustment requires a distinct requester and reviewer plus finance evidence. A legacy adjustment row by itself is insufficient.
- `release_payments` can target the Xendit-capable `payment_invoices` schema only when the exact Xendit external ID/status and historical ownership snapshot are verified. The source `xendit_invoice_id` can map to `provider_invoice_id`; it does not prove `provider_external_id` or current `provider_status`. The backend invoice is unique by release, so multiple legacy attempts need a reviewed active-attempt selection and separate archival disposition for the rest. A migration-specific idempotency key may be derived from the source payment ID, but must be namespaced and recorded as migration provenance, not represented as the original request key.

### Copyright and takedown records

- Copyright applicant type and status map by explicit lowercase-to-uppercase enum table. `ownership_percentage` becomes integer basis points only when exactly representable. Target-only terms, registration code, work position, payment idempotency, and document-media fields need validated source evidence or an approved deterministic migration rule.
- The source schema has no copyright-registration status-history table. Do not synthesize a historical sequence from current status/timestamps; any one-time migration snapshot must be labeled as a migration event, not represented as an original user/admin action. Contract template checksums and consent evidence must come from the exact retained source artifacts.
- Takedown source rows do not contain the target's declaration version/checksum. Historical `declaration_accepted=true` is not equivalent to a verifiable accepted legal text. Do not import a request as valid until that evidence and required contact fields are available.

## Implemented dry-run scope

`backend/src/recovery/soundpub-dry-run.ts` now implements a pure, no-I/O planner for Auth identity, user profiles/settings, role candidates, and supported `artist_profiles` metadata. It accepts normalized safe projections of `auth.users`, `soundpub.profiles`, `soundpub.user_roles`, and `soundpub.artist_profiles`, a run namespace, explicit parent-label approvals, and optional source-table counts. It does not read files, access a database, or write data.

- Auth export fields are limited to `id`, `email`, `email_confirmed_at`, and `created_at`; strict validation rejects unexpected fields such as password hashes or tokens without echoing their contents.
- Profile input requires exact decimal **strings** for cached balance/revenue controls and a staging-only `_unmapped_nonempty_fields` list containing field names only. Rows with unmapped values, nonzero finance controls, unresolved identities/parent profiles, managed/unlinked-account state, mismatched email evidence, or unapproved parent-label scope are blocked.
- Candidate backend accounts are always `inactive`, have `email_verified_at = NULL`, and carry `requires_reauthentication`; source confirmation time is provenance only. Candidate profile balances are set to `0.00`, never copied from cached source values.
- Role output is a review-candidate list only. It has no target `tenant_id` or `verified_at` and cannot activate backend authorization.
- Artist-profile candidates require a planned user profile, carry a separate deterministic ID crosswalk, and keep legacy verification false. Image references, Spotify fields, missing target-required timestamps, or legacy verification evidence block the row.
- The report includes identity and artist-profile crosswalks, row-level reason codes, row reconciliation, and counts for all **30** canonical tables not yet converted. `apply_supported` is always false, including when a particular row is clean.
- Eleven generated-fixture tests cover deterministic IDs, parent-label approval, duplicate/ambiguous identities, artist-profile boundaries, exact-decimal rejection, credentials/unknown fields, and incomplete table coverage. No source rows have been loaded; this is not a full-domain converter or an approved export format.

## Readiness gates before a row converter can be enabled

1. Obtain approval for a source-row export containing only the tables/columns needed for a synthetic, privacy-controlled rehearsal. Keep it outside the repository and OneDrive; do not include credentials or session material.
2. Produce an identity crosswalk and rejected/orphan report; manually adjudicate duplicates, missing Auth users, parent-label relations, role scope, and tenant scope.
3. Resolve target-only required fields (`tracks.position`, copyright terms/code/position, takedown consent evidence, media bindings) with product/legal owners; do not generate plausible-looking values.
4. Agree on the financial source of truth, exact split/rounding policy, legacy payout-state reconstruction, and opening-balance reconciliation.
5. Inventory Storage buckets/objects and retention; copy and checksum files into private storage before binding database rows.
6. Extend the new identity/profile/role/artist-profile dry-run to the remaining mapped domains, with row-level provenance, reject reasons, idempotency, counts, checksums, and exact reconciliation. Run each extension against generated fixtures first; then use an approved, isolated source snapshot. The existing `backend/src/recovery` generic rehearsal still accepts a six-kind synthetic JSON fixture and writes only to `recovery_foundation.records`; it is not a full Soundpub data converter.

Until these gates pass, the correct disposition is **not ready for row migration**. No production writes, backup restore, or cutover are authorized by this mapping.
