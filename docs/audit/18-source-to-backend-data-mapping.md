# 18 — Source-to-Backend Data Mapping

Date: 2026-11-26
Status: **PARTIALLY ROW-VALIDATED AGAINST A SCOPED BACKUP — NOT READY FOR MIGRATION OR CUTOVER**

## Purpose and evidence boundary

This is a concrete source-to-target mapping based on the 33 tables in `docs/migration/CANONICAL_SCHEMA.sql` and the target schema created by `backend/migrations/0001`–`0082`. It includes related Supabase Auth and Storage objects, which are outside those 33 `soundpub` tables.

With limited approval, the 2026-10-30 scoped backup's `soundpub` database dump was restored to a disposable PostgreSQL 15 container with networking disabled and database files on tmpfs. The 33 `soundpub` tables contain 26,204 rows; 43 foreign keys validated using a minimal local `auth.users(id)` compatibility table populated from the referenced source IDs. This does not independently prove Auth referential parity. The separate `auth/users.csv.enc` was processed in memory, retaining only `id`, `email`, `email_confirmed_at`, and `created_at`; no credential/session/MFA columns or Storage export were selected, persisted, or emitted. The backup's database/Auth/Storage artifacts were created sequentially, not as one atomic snapshot, and may not represent the current live source. Decrypted dump and disposable container were removed after validation. No target-backend or production writes occurred.

## Global conversion rules

1. **User identity is a crosswalk, never a name/email match.** Use source `auth.users.id` as the legacy key. Provision one target `backend_users.id` per resolved source identity and persist the exact relation in a controlled staging crosswalk; the current dry-run derives namespace-scoped deterministic UUIDv8 candidates. Create `external_identities.source_system/source_auth_user_id` bindings only when the provider issuer and subject are independently verified. Resolve all legacy user foreign keys through the crosswalk. A missing or ambiguous identity is an orphan: record it in `identity_references` where appropriate and block dependent writes. Never guess based on email, name, phone, or row order.
2. **Do not import credentials or sessions.** Do not copy password hashes, access/refresh tokens, verification/reset tokens, or active sessions. Require reauthentication/password setup. Create provider identities only when their issuer and subject are independently verified; profile SSO labels alone are insufficient.
3. **Imported roles remain unverified.** Source `user_roles.created_at` is not proof of backend authorization approval. Do not populate target `verified_at` from it. Backend authorization requires verified roles; role activation requires a separate reviewed approval. The source has no `tenant_id`, so the current converter emits review candidates only and does not create target role rows or assign a tenant.
4. **Preserve domain IDs only after target-emptiness and collision checks.** Keep source UUIDs for domain records where the target key is the same business record and all references can be reconciled. Record every changed ID in a durable crosswalk. Replays must be idempotent and must stop on a conflicting pre-existing target row; never truncate or overwrite target data to make a run pass.
5. **Money uses exact decimal arithmetic.** Convert IDR amounts to minor units as exact decimal-string `amount * 100`; reject values with unsupported precision, overflow, inconsistent currency, or unexplained disagreement among legacy amount columns. Do not use JavaScript floating point. Never seed the backend balance from cached profile balances or revenue totals.
6. **Storage metadata does not move bytes.** For each retained file, inventory the source bucket/key, copy bytes to the private target provider, verify size/MIME/SHA-256, then create `storage_assets`/`media_objects` and bind the domain row. A URL or path alone is not proof that the object exists or is private.
7. **Unknown or unsupported data is quarantined, not dropped silently.** Every source row must have exactly one disposition: converted, rejected with a reason, or preserved in an approved restricted archive. Conversion totals and rejected/orphan counts must reconcile to source counts.

- Parse source `numeric(18,2)` as decimal text; require exact cent precision and IDR unless a source row proves another currency. Compute minor units without floating point.

A signed finance owner must select the authoritative columns and demonstrate per-upload, per-beneficiary, and total reconciliation before mapping to `gross_amount`, `deduction_amount`, `net_amount`, allocations, and ledger events.
- For payout history, source request amount, `payout_balance_reservations`, profile balances, processed statuses, and proof objects must reconcile together. Every imported target payout requires allocations plus the matching reservation and terminal ledger event, audit row, and outbox evidence. Do not create approval/reviewer facts absent from the source.
- For `balance_adjustments`, the target's approved manual adjustment requires a distinct requester and reviewer plus finance evidence. A legacy adjustment row by itself is insufficient.
- `release_payments` can target the Xendit-capable `payment_invoices` schema only when the exact Xendit external ID/status and historical ownership snapshot are verified. The source `xendit_invoice_id` can map to `provider_invoice_id`; it does not prove `provider_external_id` or current `provider_status`. A migration-specific idempotency key may be derived from the source payment ID, but must be namespaced and recorded as migration provenance, not represented as the original request key.

## Implemented dry-run scope

`backend/src/recovery/soundpub-dry-run.ts` implements a pure, no-I/O planner for Auth identity, user profiles/settings, role candidates, supported `artist_profiles` metadata, explicitly crosswalked artist roster rows, inactive release/track bundles, a narrow notification subset, validated artist deletion requests, and a strict `app_settings` subset. The planner itself accepts normalized projections; a one-off private local runner passed selected backup projections in memory and emitted only aggregate results. No raw export or candidate payload was saved. The release/track extension is fixture-tested and was also run against an approved, presence-flag-only projection; no row values or candidate payloads were emitted.

- Auth export fields are limited to `id`, `email`, `email_confirmed_at`, and `created_at`; strict validation rejects unexpected fields such as password hashes or tokens without echoing their contents. PostgreSQL timestamp text is normalized losslessly to ISO-8601 before validation.
- Profile input requires exact decimal **strings** for cached balance/revenue controls and a staging-only `_unmapped_nonempty_fields` list containing field names only, including verification/reset-token field names. Token values must never enter the projection. Rows with unmapped values, nonzero finance controls, unresolved identities/parent profiles, managed/unlinked-account state, mismatched email evidence, or unapproved parent-label scope are blocked.
- Candidate backend accounts are always `inactive`, have `email_verified_at = NULL`, and carry `requires_reauthentication`; source confirmation time is provenance only. Candidate profile balances are set to `0.00`, never copied from cached source values.
- Role output is a review-candidate list only. It has no target `tenant_id` or `verified_at` and cannot activate backend authorization.
- Artist-profile candidates require a planned user profile, carry a separate deterministic ID crosswalk, and keep legacy verification false. Image references, Spotify fields, missing target-required timestamps, or legacy verification evidence block the row.
- Artist roster candidates require the explicit source artist→source user crosswalk, an accepted artist and label profile, matching parent-label scope, and an `artist` role candidate. The target roster candidate remains unverified; absent or ambiguous mappings block/reject instead of matching names.
- Release/track candidates require all referenced profiles and the complete source track bundle. Target releases are always `inactive`; legacy financial snapshots, custom-label releases, media references, rejection-text presence, nonempty contributor payloads, lyrics awaiting separate approval, and incomplete/non-contiguous positions block the bundle. Source track order must be provided explicitly; source order and timestamps are not treated as ordering evidence.
- Notification candidates are private and unread only. They require a resolvable recipient, resolvable optional creator, supported target type, empty source metadata, and `is_global=false`. Global announcements and `is_read=true` are blocked: the legacy schema has neither per-user global read state nor a read timestamp. Only an allowlisted empty metadata object is emitted.
- Artist-deletion requests preserve exact states and timestamps only when both mapped users have accepted target profiles and target reason constraints pass. All conflicting pending requests for one artist are blocked together.
- `app_settings` maps only target-contract keys. Money values use exact string validation and integer-dollar inputs normalize to `.00`; `auth_notice_config` must parse and satisfy the target schema. Unknown/provider settings and non-null legacy media references block the entire singleton settings candidate, preventing partial settings loss. Invalid values are rejected, duplicate keys/IDs are blocked, and diagnostics never include setting values.
- The report includes identity, artist-profile, artist-roster, audit-log/auth-event, release, track, deletion-request, notification, and application-settings provenance through deterministic IDs or explicit source row references, row-level reason codes, row reconciliation, and a reason-coded disposition for every one of the **22** remaining canonical tables: **17** require a converter, **4** are archive-only, and **1** (`rate_limits`) must be rebuilt empty. These classifications do not archive or import rows; retention procedures and the required converters remain outstanding. `apply_supported` is always false, including when a particular row is clean.
- Thirty-five generated-fixture tests cover deterministic IDs, parent-label approval, duplicate/ambiguous identities, artist-profile/roster/audit-log/auth-event/release/track/notification/deletion-request boundaries, app-settings allowlisting and bundle blocking, exact-decimal rejection, credentials/unknown fields, incomplete table coverage, and explicit dispositions for all remaining tables.

## Approved backup validation (2026-11-26)

The following are aggregate dry-run results only; issue counts overlap and do not represent unique rows:

- Auth: 198 unique source users produced 198 inactive backend identity candidates. All four selected fields validated; 197 source confirmation timestamps were non-null. No account was activated or written.
- Profiles: 0/198 rows were eligible. Blocking reasons included email-verification evidence mismatch (156), parent-label approval required (169), managed/unlinked review (106), unmapped nonempty fields (109, including legacy media or token-field presence), and nonzero cached finance (35).
- Roles: 197/198 became review-only candidates; one row was rejected because `created_at` was null. No target role was created or verified.
- Application settings: 0/20 rows produced a candidate. Nine keys were outside the target allowlist, three non-null legacy media references required a media migration, and eight otherwise mappable rows were withheld because the singleton settings bundle was incomplete.
- Notifications: 0/43 rows were eligible; no private-unread rows existed, and all 43 contained nonempty metadata.
- Artist profiles: 78 source rows exist; eight contain legacy media/Spotify fields. None was mapped because no base profile candidate was accepted. All 132 roster rows still require an explicit artist-user crosswalk. No artist deletion requests were present.
- Releases/tracks: a separate approved local projection found 291 releases and 427 tracks. It selected only the approved identity/content metadata; media URLs, lyric bodies, contributor JSON, rejection text, credentials, and finance amounts were not returned—only presence flags for the excluded fields were used. There were 290 cover-media references, 2 releases with financial snapshots, 423 tracks with legacy media, 427 with nonempty contributor payloads, 111 with lyrics, and one track rejected for an invalid required title. No track positions were supplied because the legacy table has no position column.
- The release/track planner produced 0 candidates in this run because the approved projection intentionally omitted Auth/profile rows and no identity crosswalk or track-position approvals were supplied.
